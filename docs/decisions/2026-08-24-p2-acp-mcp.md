# P2 ACP MCP session runtime

## Decision

ACP sessions receive MCP capability only after two explicit switches are on:

- `mcp.enabled: true` keeps the normal MCP capability configured;
- `mcp.acp_enabled: true` authorizes ACP sessions to start external MCP
  processes.

The second switch defaults to false. Enabling MCP in the REPL therefore never
implicitly starts a subprocess for an ACP client.

When an ACP session is created, it builds its own MCP client set from the
configured servers and performs `New`, `Start`, and `ListTools` for each one.
The advertised tools are registered in that session's independent registry as
`mcp.<server>.<tool>`. The session-local `mcp_list` reads the discovered table,
while `mcp_call` and advertised tools call only the clients owned by that
session. The REPL's `app.mcp` clients and the dynamic one-shot `mcp_*` path are
not reused.

Closing an ACP session closes every client it created. Startup failures close
any clients already started before returning the error. Client operations are
serialized with session close so a client is not closed while a call is in
flight.

## Event and safety boundary

The session log records the existing metadata-only `mcp/list` and `mcp/call`
events. MCP result text remains in the normal tool/result event path; server
output is not copied into the metadata event. The explicit switch, session
owner, independent registry, and idempotent close together prevent a remote
ACP session from inheriting the REPL's global MCP processes or lifetime.

Subagent runtime injection remains a later phase.
